# Java LLM 代理内存优化：项目复盘与面试讲述

> 本文记录 2026-10-16 的一次实际优化。主要入口为 `POST /tools/codex/v1/responses`，涉及 Java LLM 代理和底层 t-io 网络框架。
>
> 代码基线：代理提交 `e297c39`、t-io 提交 `0b9a2b4`。后续工作区改动不属于本文结论。本文未调整 JVM 堆上限，也未删除请求历史及正文记录功能。

## 1. 面试时先讲这段：一分钟版本

我做过一次 Java LLM 代理的内存优化。业务主要接收 Codex 的长上下文请求，并通过 SSE 返回响应。当时一个 Java 进程的物理内存占用约 2.41 GiB，但我没有直接判断是泄漏，也没有先调小堆上限，而是结合进程指标、`jcmd`、`jstat` 和 JFR 分配采样定位。

最终发现两类问题：应用层存在重复 YAML 解析、无插件时仍执行 Base64 和 JSON 转换；网络层虽然复用了 Socket 接收缓冲区，但半包拼接仍每次分配新缓冲区并复制全部累计数据。

我分别增加了配置缓存和插件快路径，并把半包处理改成独立的池化累积缓冲区，按倍数扩容，同时处理完成、异常和断连时的释放。整个过程中保留了请求历史和正文记录。

固定分片测试中，1 MiB 帧按 64 KiB 分片接收，新实现累积缓冲区容量合计约 1.94 MiB，旧算法同条件计算约 15.94 MiB，降低约 87.84%。代理最终通过 142 项 Java 测试，底层还覆盖了半包、异步处理和并发关闭。部署后的物理内存快照约 571 MiB，但因为负载和运行时长不同，我不会把这个快照差值直接当成优化收益。

## 2. 五分钟展开顺序

| 时间 | 内容 | 要表达的能力 |
|---|---|---|
| 前 30 秒 | 业务背景、长上下文和 SSE、内存偏高 | 从业务负载理解性能问题 |
| 30～90 秒 | 区分工作集、提交内存、堆占用；说明采样方法 | 用证据定位，避免把现象当结论 |
| 90～150 秒 | 配置缓存、插件快路径、正文复用 | 消除高频路径中的无效工作 |
| 150～240 秒 | 半包复制复杂度、VirtualBuffer 所有权和释放 | 网络框架与内存生命周期设计 |
| 最后 60 秒 | 回归测试、量化结果、限制和后续验证 | 保证正确性，并准确解释收益 |

重点展开半包累积即可，不必把所有小优化逐条背完。

## 3. 业务背景与约束

项目是一个 Java LLM 代理，支持模型路由、协议转换、插件拦截、OAuth 授权和请求记录。此次重点分析的入口是：

```text
POST /tools/codex/v1/responses
  → t-io 接收与 HTTP 解码
  → ProxyTokenInterceptor 鉴权
  → ResponsesHandler
  → ProxyService.forward
  → 路由、规则、插件与上游请求
  → SSE 转发与请求记录
```

应用使用 JDK 21 和 G1 GC；相关 t-io 模块保持 JDK 8 构建兼容。

这类业务的内存特点是：单次请求可能包含较大的上下文；流式响应持续期间，部分请求数据需要保留；正文还可能经历解析、转换、编码和记录。如果每一层都重新构造完整数据，单个请求的累计分配量会明显大于网络传输量。

优化约束：

- 保留请求历史、请求正文和响应正文的记录能力。
- 保留配置热更新、插件兼容性和 SSE 数据语义。
- 不通过修改 `-Xmx` 掩盖分配问题。
- 池化缓冲区不能在业务还使用数据时被回收复用。

## 4. 先判断：究竟是什么内存高

### 4.1 指标不能混用

| 指标 | 含义 | 不能据此推出什么 |
|---|---|---|
| Windows 工作集 `WorkingSet64` | 当前驻留 RAM 的进程页面，包含私有页和共享页 | 不等于 Java 存活对象总量 |
| 私有提交内存 `PrivateMemorySize64` | 进程私有的已提交内存，可有不驻留 RAM 的部分 | 不等于当前物理内存占用 |
| JVM committed heap | JVM 当前已提交的堆容量 | 不代表这些空间全部装着有效对象 |
| JVM used heap | 当前堆已使用空间 | 包含尚未回收的垃圾，不等于 GC 后存活集合 |
| JVM maximum heap | JVM 允许增长到的堆上限 | 不代表启动时已经占用这么多 RAM |

这些指标有包含和重叠关系，不能简单相加。

### 4.2 当时的实际观察

旧进程 PID 38680 第一次检查：

- 物理工作集约 **2.41 GiB**。
- 私有提交内存约 **3.28 GiB**。
- JVM 已提交堆约 **2.96 GiB**，堆实际使用约 **1.08 GiB**。
- 未手动设置 `-Xmx`，JVM 自动最大堆约 **7.84 GiB**。

后续自然 GC 过程中，老年代使用量曾从约 **786 MiB** 降到约 **324 MiB**，说明相当一部分对象可以回收。

因此，当时的判断是：**已有证据支持“高分配使堆扩张”，但不足以确认或排除长期内存泄漏。** 如果要确认泄漏，需要在可比负载下观察多轮 GC 后的存活集合趋势，必要时进一步分析堆转储和引用链。

### 4.3 Windows“加速”为什么不能作为 Java 优化证据

用户执行过 Windows 内存清理。前后采样中，物理工作集从约 2.29 GiB 降到约 1.43 GiB，但私有提交内存只从约 2.57 GiB 降到约 2.51 GiB，JVM 已提交堆基本维持 2.17 GiB。

这符合工作集被裁剪的现象：页面暂时不驻留 RAM，应用访问后可能重新调入。它不代表 JVM 同时释放了等量对象，也不能证明分配问题已经解决。

## 5. 如何定位到代码

使用的命令如下，PID 和输出路径按环境替换：

```powershell
Get-Process -Id <PID> |
  Select-Object WorkingSet64, PrivateMemorySize64, StartTime

jcmd <PID> VM.flags
jcmd <PID> GC.heap_info
jstat -gc <PID> 1000 6

jcmd <PID> JFR.start name=memory_diagnosis settings=profile duration=20s filename=<absolute-path>.jfr
jfr print --events jdk.ObjectAllocationSample --stack-depth 20 <absolute-path>.jfr
```

分析顺序是：先看 JVM 配置与堆使用，再观察自然 GC，然后用短时 JFR 分配采样找调用栈，最后沿真实业务路由核对源码。

JFR 中观察到的相关调用栈包括：

- `DesktopConfigService.text()` 的文件读取，以及 SnakeYAML 的解析分配。
- `PluginHostCallbacks.encode()` 的 Base64 字符串创建。
- `HttpRequestDecoder.parseBody()` 的正文字符串创建。
- `ByteBufferUtils.composite()` 的新缓冲区分配。
- `ProxyService` 请求处理中的编码和复制。

**采样权重是估算信息，不是对象当前保留量。** 本次没有把 JFR 权重直接换算成各模块精确占用，也没有使用未经验证的“每秒分配量”作为最终收益。

当时 Native Memory Tracking 未开启，因此没有得出堆外内存各组成部分的精确归因。诊断过程中未对运行中的业务进程强制 Full GC。

## 6. 应用层：减少不必要的数据转换

### 6.1 配置缓存：不仅缓存文件，还缓存解析结果

原来的配置路径存在两个开销：鉴权会重复读配置文件；工具配置查询通过 `get("")` 解析完整 YAML，最终却只取 `tool-model-aliases.codex` 等小分支。

改动分为三层：

1. 缓存配置文本和解析树，使用路径、文件大小、修改时间和文件标识检测变化。
2. 正常编辑通过元数据变化识别；另外在读取路径上做约一秒间隔的内容核对，覆盖大小和时间戳均被保留的修改。
3. 增加 `section(String... keys)`，只复制调用方需要的配置分支。

配置保存成功后立即使缓存失效；内容相同时复用解析结果。返回值采用防御性拷贝，避免业务代码修改 Map/List 后污染缓存。

这里的一秒核对是**访问驱动**，不是后台每秒轮询，也不承诺文件修改后恰好一秒完成更新。

取舍：配置树会常驻内存，但避免了大量短命解析对象；查询仍有元数据检查和局部复制。使用同步访问保证一致性，后续如果高并发下锁竞争明显，可评估不可变快照，而不是提前增加复杂度。

### 6.2 插件快路径：没有消费者就不构造数据

原实现即使没有相关插件，也可能执行：

```text
JSON 对象 → JSON 字符串 → UTF-8 字节 → Base64
          → 解码 → JSON 重新解析
```

优化后先检查对应插件是否存在；没有插件时直接使用原始数据。前后置请求拦截增加 `bodyChanged` 标记，仅在正文确实被修改后才写入 Buffer、读回和重新解析。

这比只替换序列化库更直接：最便宜的转换，是不执行本来就不需要的转换。

### 6.3 SSE：保留业务记录，按需维护插件历史

两种“历史”必须区分：

| 数据 | 用途 | 优化后的行为 |
|---|---|---|
| `capture` / `record.responseBody` | 请求详情与持久化正文记录 | 继续由 `captureBodies` 控制，保留功能 |
| `HistoryChunks` | 给兼容版本的流式插件提供最近响应块 | 仅需要它的插件存在时维护 |

插件历史继续保留最多 64 块、总计不超过 1 MiB 的限制，并维护累计字节数，避免每次遍历求和。

每条 SSE 流在开始时获取一次插件和 schema 快照，避免逐块重复查询、刷新插件配置。新启用的插件作用于新流；快照中的插件如果已停止，则跳过调用。调用与关闭使用同一同步机制，避免调用已经关闭的原生插件。

流线程不再额外捕获整个 `HttpRequest`，只显式传入连接上下文及必要正文。这减少了额外引用，但不意味着连接或响应链路完全不再持有请求相关对象。

### 6.4 正文捕获：截断不应先编码整段正文

原来的逻辑先执行 `value.getBytes(UTF_8)`，再保留前若干字节。即使记录上限只有 4 MiB，对更大的正文仍会先分配完整字节数组。

新实现针对字符串按字符对应的 UTF-8 长度寻找截断边界；已有字节数据直接使用有效区间构造结果，避免额外 `copyOf`。同时避免截断多字节字符的中间部分。

正文记录功能不变，减少的是截断过程中的临时分配。测试覆盖 ASCII、中文、多字节字符和代理对边界。

## 7. 底层重点：Socket 有缓冲池，为什么还在大量分配

### 7.1 池化覆盖范围存在缺口

`ReadCompletionHandler` 使用 `VirtualBuffer` 接收数据，解码返回后 `clear()` 并继续读取。但半包处理使用普通 `ByteBuffer`：

```java
// 原 composite() 的核心行为
int capacity = oldBuffer.remaining() + incoming.remaining();
ByteBuffer merged = ByteBuffer.allocate(capacity);
merged.put(oldBuffer);
merged.put(incoming);
```

如果还不足以解码，`DecodeTask` 随后又 `copy()` 一次累计内容。也就是说：**接收缓冲区复用了，半包累积缓冲区没有复用。**

不能简单把接收缓冲区引用留下，因为它马上会被下一次 Socket 读取覆盖。

### 7.2 重复拼接的复杂度

设一个帧长 N，每次接收 B 字节，共 k = N/B 次。原逻辑不断复制 B、2B、3B……N 大小的累计数据，多轮还会再次复制用于保存半包。

固定分片大小下，累计复制工作量随帧大小呈平方级增长，可写成 `O(B × k²)`，也就是 `O(N²/B)`。这是累计处理量，不是瞬时峰值或最终保留量。

### 7.3 新方案：独立的池化累积区

```text
Socket VirtualBuffer
  → 首次半包：复制到 DecodeTask 拥有的独立 VirtualBuffer
  → 后续数据：容量足够则直接追加
  → 容量不足：按倍数扩容，迁移已有数据
  → 完整帧：解码并交付具有独立数据的 Packet
  → 全部消费：归还累积缓冲区
```

扩容按几何级数进行，避免每次精确分配。在单个帧逐步接收的场景下，扩容迁移的累计数据量为线性级别。解码完整帧后如果仍有尾部半包，则按需压紧；大帧后只剩小尾包时收缩，避免长连接一直占着大容量。

同时取消 HTTP 解码器根据整个剩余正文增大 Socket 读取缓冲区的行为，让接收缓冲区保持配置大小，由累积区承担组包。

### 7.4 难点是所有权和释放，不是调用 allocate

此次特别处理了以下边界：

- 正常消费完成归还缓冲区。
- 解码异常、断连和主动关闭都能释放。
- 关闭不能等待正在执行的同步业务处理而形成死锁。
- 正在解码时不能提前归还并让其他请求复用。
- 异步业务处理拿到的 Packet 必须拥有自己的正文数据，不能持有将被复用的输入视图。
- SSL 解密后的明文也使用同一套半包累积机制。

实现通过解码锁、关闭标记和最终释放路径协调生命周期。并发关闭无法立即取得锁时，将释放交给正在解码的线程完成，而不是强行回收。

### 7.5 池化带来的兼容性检查

缓冲区可能是 heap、direct 或 slice，不能假设 `buffer.array()` 总能使用，也不能忽略 `arrayOffset()`。

检查过程中还完成了两项修复：

- HTTP 请求行解析在 direct buffer 路径上最多复制请求行限制对应的 8 KiB，不再复制整个剩余正文。
- WebSocket 客户端 HTTP 响应解析兼容 direct buffer 和带偏移的 heap slice。

这些修复很重要：更换内存来源后，原先隐藏在数组访问假设中的问题可能被触发。

## 8. 其他优化与收益边界

HTTP 正文字符串改为按需生成并缓存；替换正文时使字符串缓存失效。需要即时解析的 URL 表单和开发日志行为保留。

对于仍然要调用 `getBodyString()` 的 Codex 代理路径，懒转换不能消除最终那次转换。它主要避免不读取文本的路径提前构造字符串。本次也没有把所有 JSON 解析统一改成直接从字节解析。

HTTP 日期从默认每 10 ms 重新格式化，改为 UTC 秒变化时更新，使用线程安全的 `DateTimeFormatter`。这是低风险的持续分配优化，不应夸大成主要内存来源。

## 9. 验证结果：哪些数字可以讲

### 9.1 可控条件下的半包回归

测试输入：一个 **1 MiB 完整帧**，按 **64 KiB** 分成 16 次接收。

| 指标 | 结果 | 证据类型 |
|---|---:|---|
| 新实现观测到的累积缓冲区容量 | 64 + 128 + 256 + 512 + 1024 KiB | 测试实际观察到 5 个不同缓冲区 |
| 新实现容量合计 | 2,031,616 bytes，即 1.9375 MiB | 测试断言 |
| 旧 composite + copy 同条件容量合计 | 16,711,680 bytes，即 15.9375 MiB | 根据旧算法分配路径计算并断言 |
| 容量合计减少比例 | 约 87.84% | `(旧值 - 新值) / 旧值` |

正确表达：**“固定分片条件下，半包累积缓冲区的容量申请合计降低约 87.84%。”**

不能表达成“整个应用内存降低 87.84%”，也不能把池命中后复用的容量都当成新分配的操作系统内存。这不是 JMH 吞吐基准，也没有给出 CPU 或延迟收益。

### 9.2 部署后的观察

新进程 PID 21828 运行约 19.5 分钟时：

| 指标 | 旧进程首次采样 | 新进程采样 |
|---|---:|---:|
| 物理工作集 | 约 2.41 GiB | 约 571 MiB |
| 私有提交内存 | 约 3.28 GiB | 约 1.61 GiB |
| JVM 已提交堆 | 约 2.96 GiB | 约 1.35 GiB |
| 堆实际使用 | 约 1.08 GiB | 约 633 MiB，采样末尾 |
| 最大堆 | 约 7.84 GiB | 约 7.84 GiB，未调整 |

新进程约 5 秒采样期间有一次年轻代 GC，耗时约 3 ms，没有 Full GC。

这是部署观察，不是严格 A/B 测试：两次进程运行时长、流量、并发和 Windows 工作集状态不同。因此可以说“部署后观察到更低占用”，不能说“已经证明生产内存稳定降低某个百分比”。

- 覆盖 direct buffer、heap slice、正文缓存失效和 HTTP 日期按秒复用。
- 前端生产构建和同期 OAuth 界面测试通过。
- 最终打包后对比嵌入 JAR 与新构建 t-io 依赖的哈希，确认交付产物包含底层修复。

本次没有完成同负载长时压测，也没有测得可声明的 P95/P99 延迟或吞吐提升。

## 10. 面试官常见追问

### 为什么不直接调小 Xmx？

堆上限可以限制内存增长，但不能消除重复分配。过早缩小可能让 GC 更频繁。本次明确先改代码，保留 JVM 参数，后续再根据负载和资源预算设置容量。

### 怎么区分内存泄漏和分配率高？

分配率高主要看对象创建速度和 GC 行为；泄漏需要看原本应该释放的对象是否长期被引用。要在相似负载下比较多轮 GC 后的存活集合，并结合引用链分析。一次工作集高或老年代高都不能单独证明泄漏。

### 有 VirtualBuffer 为什么还需要改？

池化只覆盖 Socket 接收层，`composite()` 和保存半包的 `copy()` 仍然使用 `ByteBuffer.allocate()`。要沿所有权和调用链检查覆盖范围，不能只看到项目里有缓冲池就认为所有分配都已复用。

### 为什么不直接让 composite 从池里分配？

这样可能减少新建缓冲区，但每次复制全部累计数据的复杂度没有变化。关键是改变累积策略，让容量够用时只追加新数据，再配合池化和正确释放。

### 为什么不用零拷贝？

当前协议解码与业务接口需要独立正文，接收缓冲区又会马上复用。直接共享视图需要引用计数或明确的释放协议，尤其异步业务会增加复杂度。本次优先消除重复全量复制，保留必要的所有权边界，没有声称实现零拷贝。

### 池化会不会反而让内存不降？

会有这种可能。池化降低分配频率，但池和连接如果长期保留大缓冲区，可能提高常驻内存。因此需要检查归还路径、大缓冲区收缩和池的空闲回收，不能只统计命中率。

### 配置缓存会不会读到旧数据或被改坏？

普通编辑通过元数据变化检测，保留元数据的修改通过访问时的周期内容核对补充；程序内保存立即失效。返回局部分支的防御性拷贝，调用者修改不会污染缓存。代价是仍有元数据检查、锁和局部复制，属于当前实现的明确取舍。

### 为什么每条流固定插件快照？

一条流中的数据处理语义应尽量一致，同时避免逐块刷新插件配置。新启用插件从新流开始生效；已经停止的插件通过受保护调用跳过，防止访问已关闭的原生资源。

### 优化有没有牺牲可观测性？

没有删除请求历史和正文记录。只按需维护插件专用历史，减少记录过程中的重复编码和复制，并对 UTF-8 截断做边界处理。

### 你如何证明没有破坏异步业务？

测试延迟执行业务处理，并覆盖原输入被后续数据覆盖的情况，验证 Packet 正文仍然正确；并发关闭测试验证活动累积缓冲不会提前归还，处理结束后能释放。

### 如果继续优化，下一步做什么？

建立固定请求集，控制上下文大小、并发、SSE 持续时间和插件配置，先预热，再比较分配速率、GC 后堆占用、GC 时间、P95/P99、吞吐和进程提交内存。必要时重启启用 NMT 分析堆外组成，再根据证据决定是否进一步优化配置锁竞争、协议转换或正文表示。

## 附：同期 OAuth 功能，可作为另一个小案例

同期还解决了服务端部署的 OAuth 回调问题：用户浏览器跳转到 `127.0.0.1` 时，访问的是用户自己的电脑，而授权监听器在服务器上。

新增页面输入框，让用户粘贴完整回调 URL；管理后端校验待授权会话、有效期、回调端口和路径，再由服务器向自身回调地址发送 HTTP 请求。请求不走上游代理，也不跟随重定向。插件 OAuth 则复用已有会话回调分支。

这个入口不是通用 URL 代理。它受管理鉴权和 OAuth 会话约束，避免把功能做成任意服务端请求入口。可用来介绍对 `localhost` 网络语义、OAuth state 和接口边界的理解，但不应算进内存优化收益。
